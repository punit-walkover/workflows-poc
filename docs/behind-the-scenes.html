Behind the scenes, feature by feature

A short tour: for each thing you can do in the POC, what you do on screen and what the code does in the background. For the full detail, see the backend deep dive.

What you doWhat the code does, in order
Every run is one durable loop: decide→act→advance→flush→wait (recv)→apply↺ · each step checkpointed by DBOS, so a restart never repeats work

Building a workflow editor

Create and save

You: create a workflow from a template or blank, edit it, click Save.

  1. The workflow is stored as JSON (steps or graph) in the workflow row.
  2. Every save is validated; a draft may keep issues.
  3. The save only applies if row_version still matches; otherwise 409 "changed elsewhere".
workflows.service.ts saveWorkflow

Publish and enable

You: click Publish; toggle Enabled.

  1. Publish is refused while there are issues.
  2. Otherwise a frozen copy is inserted as workflow_version N+1 and the workflow is enabled.
  3. Runs point at a version, so live chats keep the version they started with.
publishWorkflow · patchWorkflow

List editor and Go to step

You: write steps, add If/Else conditions and "Go to step" jumps.

  1. Stored as a tree: step, branch (cases with nested steps), goto.
  2. Validated: max 15 steps, nesting depth 2, Go to limit 1–100.
  3. At run time a goto is deterministic: a jump back re-runs the steps in between.
validator.ts · tree.ts · flow.ts treeFlow

Canvas editor

You: open in canvas, drag cards, draw arrows, drag blocks between groups.

  1. Conversion turns the tree into groups and arrows (treeToGraph), keeping ids.
  2. React Flow draws it; every edit is a pure function on the graph, which also gives undo.
  3. Saved as workflow.graph; validated for reachability, one arrow per output and limits on loops.
graph.ts · web canvas/*

Validation

You: see issues under the editor; Publish is blocked until they're fixed.

  1. Checks text, condition order, known @actions and {{variables}}.
  2. On the canvas it also checks groups can be reached, arrows are valid and every loop has a limit (Tarjan cycles).
  3. Returns the issues plus the action keys and step count stored with the workflow.
validator.ts · graph.ts validateGraph

Variables

You: add variables in the palette, use {{name}} anywhere.

  1. Names are saved in graph.variables and copied into each version.
  2. Values live per run in facts.vars, filled by inputs and Save response.
  3. Built-ins (customer name/email, today) are computed when a run loads, never stored.
context.ts loadRun

Blocks at run time runner

Routing a new chat

You: send the first message in the playground or widget.

  1. The message is saved and the reply happens in the background.
  2. The LLM gets the enabled workflows and recent chat and picks one with a confidence.
  3. ≥ 0.7 starts a run; 0.4–0.7 asks a question; "wants a human" hands over; otherwise a plain answer.
run-control.ts onCustomerMessage · decider.ts route, gate

Starting a run

You: nothing; routing chose a workflow.

  1. A workflow_run row is inserted at the first block (one active run per chat).
  2. A DBOS workflow run:<id> starts the loop.
  3. DBOS resumes it after any restart.
startRun · workflow.ts

AI step

You: write an instruction, maybe mentioning @action.

  1. The LLM returns JSON: complete, ask the customer, call an action, or escalate.
  2. The code validates it, then says, waits, runs the tool or ends.
  3. After a tool succeeds with nothing said, the step runs once more so the AI can report the result.
steps.ts decide/act/advance · decider.ts decideStep

Text bubble

You: add a Text bubble with a fixed message.

  1. No AI call: the text is filled with variables (unset ones show blank).
  2. It is queued as a word-for-word message and the run moves straight on.
  3. On send, it goes out as its own chat message.
steps.ts say · flush

Input

You: add a Text/Email/Number/Phone input and pick a variable.

  1. It sends the question, remembers when it asked, and waits.
  2. The next customer message is checked against the format.
  3. A valid answer is saved to the variable. An invalid one gets the retry message; after 3 tries the chat is escalated.
steps.ts ask · blocks.ts checkAnswer

Conditions

You: choose AI (plain words) or Rules (variable · comparison · value).

  1. AI mode: the LLM judges each case true or false; the code picks the first true one.
  2. Rules mode: compared in code with no AI, using AND/OR.
  3. The chosen case is saved and the run follows that case's arrow.
decider.ts chooseCase · blocks.ts chooseByRules

Save response

You: under an AI step, map response fields to variables, picking from the last real response.

  1. The picker reads the newest successful action_run.result; no tool is run.
  2. When the action succeeds, each path (items[0].name…) is read into facts.vars.
  3. Missing fields are skipped and logged as response_saved.
blocks.ts getPath, saveResponse · /actions/:key/sample

Loops

You: draw an arrow back, set "repeat at most N", optionally "ask again".

  1. The run keeps a trail of finished blocks; an arrow to one on the trail is a loop.
  2. Each loop counts a visit; over the limit, the chat goes to a teammate.
  3. Repeated blocks lose their old answers; "ask again" also forgets the customer's earlier replies.
steps.ts follow, rerun

Sending replies

You: see the bot's messages appear.

  1. Blocks never send directly; they add to the run's outbox.
  2. Once per turn, AI notes in a row are merged into one reply; bubbles go out as written.
  3. Each becomes a message row and a message_sent event.
steps.ts flush · decider.ts compose

Tools and people actions · approvals

Running a tool

You: mention @lookup_order (or any action) in a step.

  1. The AI's arguments are checked against the action's input schema.
  2. An action_run row keyed by run · step · visit makes the call happen once only.
  3. It runs the mock handler, a viaSocket flow or a viaSocket app action, and stores the result.
execute.ts validateArgs, executeAction

Creating viaSocket tools

You: open the tool builder on the Actions page and publish a tool.

  1. The builder is opened with a signed token from /integrations/builder-token.
  2. Its "flow" event is sent to /actions/from-flow, which creates or updates the action with its schema.
  3. New tools start with approval required; calls POST the arguments to the flow URL.
viasocket.ts · actions.controller.ts

Approvals

You: see the red dot, open the chat, approve or reject.

  1. A step needing approval opens an approval_task and the run waits.
  2. Deciding sends an approval_decision signal to the run (keyed by task, so only once).
  3. Approved actions run then; evidence decisions are stored for the next condition to read.
steps.ts openTask, apply · runs.controller.ts

Escalation

You: use @escalate_to_human, or the run hits a limit.

  1. The run ends as escalated with a hand-over message.
  2. Later messages in that chat get a system note and the bot stays quiet.
  3. Loop limits, 3 failed asks and approval timeouts end the same way.
steps.ts advance · run-control.ts

Reminders and expiry

You: leave a chat waiting.

  1. Waiting sets a deadline on the run's DBOS recv; there is no cron.
  2. After 2 minutes, one reminder; after 10, the run expires.
  3. An approval not decided in 30 minutes expires and escalates.
workflow.ts recv · steps.ts apply(null)

Pause, resume, cancel, retry

You: use the buttons on the run panel.

  1. Each button sends a signal; it is refused if the run's status doesn't allow it.
  2. Pause saves what the run was waiting for, and resume restores it.
  3. Retry re-runs a failed step; cancel ends the run and its approvals.
run-control.ts signal · steps.ts apply

Chats and visibility playground · widget · LLM

Playground

You: chat as a customer or as the team; watch the run panel.

  1. One poll (GET /conversations/:id) returns messages, runs, events, approvals and tool calls.
  2. Team messages are shown and given to the AI as context, but don't wake the run.
  3. Attachments are stored on disk with a checksum and linked to messages.
playground.controller.ts · conversations.ts

Chat widget

You: embed the chatbot in another product.

  1. A separate /widget API starts a chat from an email.
  2. It shows only customer, bot and team messages, plus "typing" and "waiting for team" flags.
  3. Messages go through the same routing and runner as the playground.
widget.controller.ts

Run panel

You: watch steps tick, the yellow box move, skipped groups strike out.

  1. Every action of the runner is a run_event with the block id.
  2. The panel marks blocks done from events and shows answers and saved variables from facts.
  3. "Show DBOS checkpoints" lists the durable steps DBOS recorded.
run-panel.tsx · /runs/:id/dbos-steps

Talking to the LLM

You: nothing; it happens on each AI decision.

  1. The server logs in to GTWY with a signed token and reuses one agent.
  2. Each call overrides the system prompt for its job (route, step, case, merge, reply).
  3. JSON answers use temperature 0; a session error retries once.
llm/gtwy.ts · llm/decider.ts

Gaps worth knowing: there is no authentication on any endpoint, viaSocket flow URLs are stored in plain text, and tool calls run inside a database transaction. The deep dive lists these with details.
