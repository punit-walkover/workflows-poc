Why a canvas

Until now, a workflow was a list: steps, conditions with nested steps, and "Go to step" jumps. A list is fine for straight procedures. It gets hard to read once a flow branches, joins back together, or loops.

The canvas shows the same procedure as cards joined by arrows, like Typebot. You can see the whole flow at once, every branch has its own arrow, and loops show up as dashed blue arrows with their repeat limit printed next to them.

Both kinds of workflow keep working. A workflow with a saved graph opens in the canvas and runs as a graph. A workflow without one stays in the list editor and runs as before. The "Open in canvas" button converts a list workflow once.

The saved graph

The canvas saves one JSON object. Migration 0007_workflow_graph.sql adds a nullable graph jsonb column to both workflow (the draft) and workflow_version (the published copy). Publishing copies the graph into the new version, the same way it copies steps.

WorkflowGraph {
  start:  string                      // id of the Start group
  groups: GraphGroup[]                // the cards
  edges:  GraphEdge[]                 // the arrows
}
GraphGroup { id, title, x, y, items: GraphItem[] }
GraphItem  = { id, type: 'step', content: Inline[] }
           | { id, type: 'condition', cases: { id, kind: 'if'|'else_if'|'else', condition: Inline[] }[] }
GraphEdge  {
  id,
  from: { groupId, itemId?, port? }   // a group's end, or one case of a condition
  to:   { groupId, itemId? }          // a whole group, or one step inside it
  maxVisits?: number                  // repeat limit, 1 to 100 (loops only)
  fresh?: boolean                     // "ask again": forget answers on each repeat
}

The pieces on a card

Group (card): a run of steps that happen in order. You drag it by its header.
Step: one instruction for the AI. It can mention @actions and {{variables}}.
Condition: a list of cases. Each case has its own output dot.
"then" dot: where the run goes after the group's last item.
Yellow box: the step that is running right now (in the run panel).

Arrows start from a dot: either a group's "then" dot or one case of a condition. An output has at most one arrow, and drawing a new one replaces the old. An arrow can land on the top of a card (start that group) or on a single step inside a card (start partway through it). Landing on a step is what lets "Go to step" point anywhere, forward or back.

Item ids are kept when a list workflow is converted. That way facts, run events and the step highlight in old runs still line up.

The editor

The canvas is a plain div moved with a CSS transform: translate(x, y) scale(z). Cards sit inside it at their saved x, y. An SVG layer under the cards draws the arrows. This is the same approach Typebot uses, and no canvas library is needed.

How arrows find their ends

Every dot and every drop point registers its element under a key, such as src:<groupId>, src:<itemId>:<caseId> or tgt:<itemId>. After each render, the canvas measures each element's height inside its card, and a ResizeObserver measures again when a card grows. An arrow is then drawn from the source card's x and that y offset to the target's. The path is orthogonal (2 to 5 straight segments) with rounded corners. That drawing code is the part ported from Typebot.

Editing helpers

All edits go through small pure functions in web/src/lib/graph.ts, such as connect, removeItem and addCase. Each takes a graph and returns a new one. Undo is just a stack of earlier graphs. Removing a card, a step or a case also removes every arrow that touched it, so no arrow is ever left pointing at nothing.

Running a graph

The runner itself didn't change: it is still the durable DBOS loop decide → act → advance → flush → wait → apply. What changed is how it finds the next step. That now goes through a small Flow interface, with one version for lists and one for graphs.

interface Flow {
  kind: 'tree' | 'graph'
  first(): string                          // first item to run
  node(id): Node                           // a step or a condition
  next(id): Jump                           // after a step finishes
  afterCase(id, caseId): Jump              // after a condition picks a case
}
type Jump = { to: string | null; edge?: GraphEdge }
flowOf(version) = version.graph ? graphFlow(version.graph) : treeFlow(version.steps)
flowchart LR
  A[Step finishes] --> B{More items in this group?}
  B -- yes --> C[Next item in the group]
  B -- no --> D{Group has a 'then' arrow?}
  D -- yes --> E[Follow the arrow]
  D -- no --> F[Run completes]
  G[Condition picks a case] --> H{Case has an arrow?}
  H -- yes --> E
  H -- no --> B
  E --> I{Target already ran in this run?}
  I -- no --> J[Go to target]
  I -- yes --> K[Loop back: count the visit, check the limit]
  • Inside a group, items run top to bottom.
  • At the end of a group, the run follows the group's "then" arrow. If there's no arrow, the run is done.
  • A condition uses the same AI case chooser as list workflows. Each case is judged true or false, then the run follows the chosen case's arrow. If that case has no arrow, the run carries on to the next item in the group.
  • Approvals work the same way: when the team decides, the runner calls next() from the step that was waiting.

The playground's run panel draws a graph run as a list of groups, with Start first. The running step gets the yellow box, finished steps get a ✓, and conditions show the case that was chosen.

Loops and limits

A graph can loop. In the damaged-item example, if the photo is unclear the run goes back to "ask for a photo". The runner tells a loop from a normal forward move with a trail: a list in the run's facts of every item that has finished.

  1. When the runner follows an arrow to an item that is already on the trail, that arrow is a loop back.
  2. The visit counter for that arrow goes up. If it goes over the arrow's maxVisits, the run ends with the reason loop_limit instead of looping forever.
  3. The facts for the steps being repeated are cleared, and those items are taken off the trail.
  4. With "ask again" on, earlier answers are forgotten, so the AI asks the customer fresh. With it off, the AI keeps what it knows and sees the earlier results as "previous".
  5. The transcript is marked with a since point, so the AI knows which messages belong to the new pass.

The limit can be 1 to 100, the same as "Go to step" in the list editor. On the canvas, loop arrows are dashed blue and labelled "↺ max N", or "↺ no limit" until one is set.

Validation rules

validateGraph runs when you save and blocks publishing until there are no issues. The editor shows the same issues as notices.

Repeat limit is 1 to 100repeat limit must be 1 to 100
At most 50 stepsToo many steps: N of 50
Actions are enabled and variables are known@key doesn't exist or is disabled / Unknown variable

Loops are found with Tarjan's algorithm for strongly connected components. A group of cards that can all reach each other is one loop, and at least one arrow inside it must have a limit. That is enough to guarantee every run ends.

List to canvas

POST /workflows/:id/canvas runs treeToGraph(steps), saves the result as the draft's graph, and the page reloads into the canvas.

  • Steps go into the current card in order.
  • A condition ends its card. Each case's steps get their own card, titled with the first few words of the case. A "Then" card holds whatever came after the condition, and every case joins it.
  • A "Go to step" becomes an arrow to the target step, with the same limit and "ask again" setting. If a case holds only a Go to step, its arrow starts directly from that case.
  • Empty "Then" cards are skipped: arrows into them go straight to where they lead.
  • Cards are laid out in columns by distance from Start (400px apart), then stacked using an estimated card height.

Both built-in templates convert with no validation issues.

What came from Typebot

Typebot was used as a reference for how its canvas works. Only one small piece of code was adapted: the arrow path drawing in web/src/components/canvas/edge-path.ts, which carries an attribution comment. Everything else was written fresh with the same approach.
