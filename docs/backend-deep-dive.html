Foundations

The big picture

The POC is two apps. web/ is the editor and playground. server/ owns everything that matters: workflows, runs, actions, approvals, and every call to the LLM and to viaSocket. The web app only talks to the server over HTTP and polls for updates.

Three ideas carry the whole design:

  1. A workflow is data. It is JSON (a list tree or a canvas graph) stored in Postgres. Publishing freezes a copy as a version; runs always point at a version, so editing never disturbs a live conversation.
  2. A run is a durable loop. Each conversation's run is one DBOS workflow. Every unit of work is a checkpointed step, so a crash or restart resumes exactly where it stopped, without repeating side effects.
  3. The AI decides; the code acts. The LLM only returns a JSON decision ("ask the customer", "call this action", "this case is true"). The server validates that decision and does the work itself: running tools, opening approvals, moving the cursor.

Boot, config, env

src/main.ts · src/app.module.ts · src/config.ts · src/db.ts

  1. main.ts imports runner/workflow first, so the DBOS workflow function is registered before launch.
  2. DBOS.setConfig({ name: 'workflows-poc', systemDatabaseUrl: DATABASE_URL }) then DBOS.launch(). DBOS keeps its own tables in the dbos schema of the same database, and on launch it resumes every unfinished run.
  3. seedWorkflows() creates and publishes the templates if the workflow table is empty.
  4. Nest starts with an 8 MB JSON body limit (attachments arrive as base64), CORS for CORS_ORIGINS, and listens on PORT.

AppModule only registers controllers (Workflows, Actions, Integrations, Playground, Widget, Runs). There are no Nest providers; services are plain exported functions. db.ts is a pg pool (max 10) with three helpers: q (rows), one (first row or null) and tx (begin/commit/rollback).

Building workflows

Create, save, publish

src/workflows/workflows.service.ts · workflows.controller.ts

stateDiagram-v2
  [*] --> Draft: POST /workflows
  Draft --> Draft: PUT /workflows/:id (save, may have issues)
  Draft --> Published: POST /publish (no issues)
  Published --> Draft: edit → has_unpublished_changes
  Published --> Enabled: publish turns it on
  Enabled --> Disabled: PATCH enabled=false
  Disabled --> Enabled: PATCH enabled=true (needs a published version)
  Draft --> Archived: DELETE
  Enabled --> Archived: DELETE
  • Create: from a template or one empty step. A clashing name gets a number suffix.
  • Save (saveWorkflow): validates, but a draft may be saved with issues. Optimistic concurrency: the update only applies WHERE row_version = $sent and bumps it. If someone else saved first, the server returns 409 ("changed elsewhere, reload"). steps or graph left out of the body keep their current value.
  • Publish (publishWorkflow): refuses with 400 and the issue list if validation fails. In one transaction it inserts workflow_version = next number with a copy of name, when_to_use, steps, graph and action_keys, points published_version_id at it, clears has_unpublished_changes and sets enabled = true.
  • Enable/disable (PATCH): enabling needs a published version. Only enabled, non-archived, published workflows are candidates for routing.
  • Archive (DELETE): sets archived_at and disables. Versions stay, so old runs still resolve, and the name becomes reusable.
Runs hold a workflow_version_id, never a workflow id. Publishing v2 while a v1 run is waiting for the customer changes nothing for that run.

List and canvas formats

src/types.ts · src/workflows/tree.ts · src/workflows/graph.ts

A workflow is stored in one of two shapes. Both use the same inline text format: an array of parts, {t:'text'}, {t:'action', key} for @action, and {t:'var', key} for {{variable}}.

List tree (workflow.steps)

step   { id, type:'step', content }                         // an AI instruction
branch { id, type:'branch', cases:[{ id, kind:'if'|'else_if'|'else', condition, steps:[...] }] }
goto   { id, type:'goto', target, max_visits, fresh? }       // jump to another node

Canvas graph (workflow.graph)

{ start, variables?: ["order_id", ...],
  groups: [{ id, title, x, y, items: [
      { type:'step',      content, save?: [{ path, var }] }          // AI step (+ Save response)
      { type:'bubble',    content }                                  // fixed message
      { type:'input',     prompt, saveAs, format, retry? }           // ask, check, save
      { type:'condition', mode?:'ai'|'rules', cases:[{ kind, condition, rules?, join? }] } ] }],
  edges: [{ id, from:{ groupId, itemId?, port? }, to:{ groupId, itemId? }, maxVisits?, fresh? }] }

An edge starts from a group's end (no itemId) or from one case of a condition (itemId + port = case id). It lands on a group (start at its first item) or on one item inside a group.

Converting a list to a canvas

POST /workflows/:id/canvas runs treeToGraph(steps) and saves the result as the draft's graph. Item ids are kept, so history lines up. A condition ends its group: each case gets its own group, a "Then" group collects what follows, and every case joins it. A Go to becomes an edge to its target with the same limit. Empty groups are bypassed. layout() places groups in columns by distance from Start.

Templates and seeding

Two list-format templates: Order refund (ask → @lookup_order → within 30 days: @refund_order and confirm; older: @escalate_to_human; not found: explain) and Damaged item return (adds a photo, @request_approval, and a Go to back to the photo step with max_visits: 2, fresh: true when the photo is unclear). Running workflows

Routing a message

src/playground/conversations.ts · src/runner/run-control.ts onCustomerMessage · src/llm/decider.ts route, gate

flowchart TD
  M[Customer message saved] --> A{Active run?}
  A -- yes --> S[signal run: customer_message]
  A -- no --> E{Last run escalated?}
  E -- yes --> Q[system note: bot stays quiet]
  E -- no --> R[route: LLM picks a workflow]
  R --> G{gate}
  G -- wants_human ≥ 0.8 --> H[bot: passing you to a teammate]
  G -- confidence ≥ 0.7 --> ST[startRun with published version]
  G -- 0.4–0.7 + question --> CL[bot asks the clarifying question]
  G -- else --> FR[freeReply: plain helpful answer]
  • postCustomerMessage inserts the message and fires onCustomerMessage without waiting, so the HTTP call returns immediately and the client polls.
  • route() sends the enabled workflows (id, name, when to use) and the last 6 messages to the LLM and gets back { workflow_id, confidence, wants_human, question, reason }. An unknown id is treated as no match.
  • gate() turns that into one of four outcomes using fixed thresholds. Every outcome is logged as a system message ("Routing: start (confidence 0.99) …"), which the playground shows and the widget hides.

The durable run loop

src/runner/workflow.ts · src/runner/steps.ts · src/runner/run-control.ts startRun

startRun inserts the workflow_run row (cursor = first block, facts seeded with the customer's name and email), logs run_started, and starts the DBOS workflow with id run:<runId>. That id makes the start idempotent and lets anyone send it signals.

for (;;) {
  if (mode === 'run') {
    dec = runStep(decide)              // ① what should happen at the cursor?
    out = dec is call_action ? runStep(act) : null   // ② run the tool / open approval
    r   = runStep(advance)             // ③ apply: facts, cursor, status
    if (r.next === 'continue') continue   //    next block right away, same turn
    runStep(flush)                     // ④ send this turn's messages
    if (r.next === 'end') return
  }
  s = DBOS.recv('signal', deadline)    // ⑤ sleep until a signal or a timer
  a = runStep(apply(s))                //    customer reply, approval, pause, timer…
  runStep(flush)
  mode = a.next === 'run' ? 'run' : 'wait'
}

Each runStep is checkpointed by DBOS. On restart, completed steps return their saved result instead of running again, so a tool call or an LLM decision is never repeated. Every step reads fresh state with loadRun() and writes it with saveRun(); nothing important lives in workflow memory.

StepJobCalls the AI?
decideLooks at the block under the cursor and returns a Decision: end, error, case, goto, say, ask, or step (with the AI's decision)Only for AI steps and AI conditions
actValidates the chosen action and runs it, or opens an approval task, or escalatesNo
advanceStores results and variables, moves the cursor (following edges), sets the status and what to wait forNo
flushTurns the outbox into chat messagesOnly to merge several AI notes
applyHandles a signal or a timer through the run's state machineNo

Run statuses: running, waiting_customer, waiting_approval, paused, failed (all "active"), and the terminal completed, escalated, expired, cancelled.

Finding the next block

src/runner/flow.ts

The runner never reads the workflow JSON directly. It asks a Flow, built by flowOf(version): a graphFlow when the version has a graph, otherwise a treeFlow.

interface Flow {
  first()                    // where a run starts
  node(id)                   // the block as a runner node: step | branch | goto | say | ask
  next(id)                   // after a block finishes
  afterCase(id, caseId)      // after a condition picks a case
}
  • treeFlow: next sibling, else the node after the enclosing branch. A case continues at its first step.
  • graphFlow: next item in the same group; at the end of the group, follow the group's "then" arrow; no arrow means the run is done. A case follows its port's arrow; a case with no arrow falls through to the next item. Bubbles map to say nodes, inputs to ask, conditions to branch (with their mode).

Every move goes through follow() in steps.ts, which resets attempt counters and, for graphs, maintains the trail used to detect loops.

AI steps

src/runner/steps.ts decide/act/advance · src/llm/decider.ts decideStep

decideStep sends the step text (with variables filled in), the allowed actions and their argument schemas, the customer, the known facts (collected, variables, outputs, previous results) and the transcript. The model must answer one JSON object:

{ "decision": "complete" | "ask_customer" | "call_action" | "escalate",
  "message": "…", "collected": {}, "missing": [], "action": { "key": "", "args": {} }, "reason": "…" }
DecisionWhat the runner does
completeSays the message and moves on. A step that mentions an action can't complete before that action has run; the runner counts it as invalid and asks again (max 2, then the run fails).
ask_customerSays the message, sets waiting_for customer (with reminder and expiry), status waiting_customer. After 3 asks on one step, it escalates.
call_actionact checks the action is mentioned in the step and enabled, validates the args, then executes it or opens an approval. On success the result goes to outputs[stepId] and Save response runs.
escalateSays the message and ends the run as escalated.

Speaking after an action

The AI writes its message before it sees the action's result. So when an action succeeds and the AI said nothing yet, the runner runs the same step once more. The prompt then says "this step's action already ran, its result is outputs.<id>, don't call it again; complete with a message". If the model asks for the action again anyway, act returns the stored result instead of running it twice.

decide retries the LLM call once on failure. Invalid actions (not allowed, disabled, bad args) are retried up to twice with a "follow the rules exactly" hint before the run fails.

Conditions

src/llm/decider.ts chooseCase · src/runner/blocks.ts chooseByRules

  • AI mode: chooseCase sends every non-else condition with its id, the facts and the last 6 messages. The model judges each one true or false with a reason; the code then picks the first true case, else the Else case, else none.
  • Rules mode (canvas): no AI. chooseByRules checks each case's rules against the run's values (collected + built-ins + workflow variables). Operators: =, !=, contains (text, case-insensitive), >, < (numbers), empty, not_empty, joined by AND or OR. The first matching case wins; Else catches the rest.

Either way the result is stored in facts.cases[conditionId], logged as case_chosen, and the run follows flow.afterCase().

Bubbles and inputs

src/runner/steps.ts · src/runner/blocks.ts checkAnswer

Text bubble

decide returns { kind:'say' } without calling the AI. advance renders the text (a declared variable with no value shows as blank) and pushes it to the outbox as verbatim, then moves on in the same turn. Several bubbles in a row become several chat messages.

Input

  1. First visit: decide sees no facts.asked[id] and returns "ask". advance sends the prompt verbatim (if any), records asked[id] = now, and waits for the customer.
  2. When the customer replies, the run resumes at the same block. decide takes the first customer message after asked[id] and runs checkAnswer(format, text):
    • email: extracts an address · number: extracts a number (commas allowed) · phone: 7–15 digits · text: any non-empty text.
  3. Valid: the value goes to facts.vars[saveAs], asked[id] is cleared, the run moves on. Invalid: the retry message (custom or a default per format) is sent and it waits again. After 3 tries the run escalates.

loadRun builds the vars map used for {{name}} in every block: built-ins plus every declared variable that has a value. Workflow variables live in their own facts.vars so the AI can't overwrite a customer's answer.

Save response

An AI step can list save: [{ path, var }]. When its action succeeds (in advance, or in apply after an approval), saveResponse() reads each path with getPath() (delivered_at, items[0].name, [0].item, items.length) and stores found values in facts.vars. Missing paths are skipped, and the event response_saved { saved, missing } records both. varsBy[stepId] remembers which variables the step filled, so "ask again" can clear them on a loop back.

The editor's field picker calls GET /actions/:key/sample, which returns the newest successful action_run.result for that action. No action is run just to fill the picker.

Go to step and loops

src/runner/steps.ts rerun, follow

Loops are how a workflow says "go back and try again" (for example, "the photo is unclear, ask for another"). Both formats share one bookkeeping function, rerun():

  • Counts the visit (facts.visits[key]). Past the limit, the run ends as escalated with reason loop_limit, and the customer is told a teammate will reply.
  • For every block that will run again: its old output moves to previous, and its case, attempts and asked marker are cleared. A since marker is added so the AI sees a note in the transcript at the point the loop happened.
  • Ask again (fresh): also forgets the AI's notes and the workflow variables those blocks filled. Without it, the AI keeps what it knows and asks only for what is missing.

List format: Go to step

A goto node is deterministic (no AI). Forward jumps skip ahead and re-run nothing; backward jumps re-run everything between the target and the goto (between() in document order).

Canvas: loop arrows

follow() keeps facts.trail, the list of finished blocks in order. If an arrow leads to a block already on the trail, that arrow is a loop back: it calls rerun() with the arrow's maxVisits and fresh, and cuts the trail back to that block. This works for arrows into the middle of a group too.

Sending messages

src/runner/steps.ts flush · src/llm/decider.ts compose

Nothing is sent to the customer in the middle of a step. Blocks push into workflow_run.outbox, and flush sends everything once per turn, in order:

  • AI notes in a row (strings) are merged into one reply by compose(), which keeps every fact, amount and date. One note is sent as-is with no LLM call; if merging fails, they are joined.
  • Bubble and input text ({ text, verbatim: true, nodeId }) is sent word for word as its own message.

Each message is a message row with role='bot' and the run_id, plus a message_sent event tagged with the block that wrote it.

Waiting, reminders, expiry

There is no cron. Every timer is the deadline of the run's DBOS.recv(). When recv times out it returns null, and apply(null) handles the timer.

Signals and run control

src/runner/run-control.ts signal · src/runner/runs.controller.ts · steps.ts apply

Every outside event reaches a run through one function, signal(runId, s, idempotencyKey). It checks the signal is allowed in the run's current status, logs a signal event, and calls DBOS.send('run:<id>', s, 'signal', key). The key de-duplicates: a customer message uses msg:<messageId>, an approval task:<taskId>.

StatusAllowed signals
running, waiting_customercustomer_message, pause, cancel
waiting_approvalcustomer_message, approval_decision, pause, cancel
pausedcustomer_message, resume, cancel
failedcustomer_message, retry_step, cancel
  • customer_message: while waiting for the customer, resume at the cursor. While waiting for approval, reply "our team is still reviewing this".
  • pause / resume: pause saves paused_from (status and what it was waiting for); resume restores it or continues at the cursor.
  • retry_step (only from failed): resets the step's invalid-attempt counter and runs it again.
  • cancel: ends the run and cancels its pending approvals.

Team messages (POST /conversations/:id/team-messages) are not signals: they appear in the chat and in the AI's transcript as "Teammate", but they do not wake the run.

Tools and people

Actions

src/actions/execute.ts · src/actions/actions.controller.ts

An action is a row in the action table: key, name, description, JSON input schema, read/write, requires_approval, and a source that says how to run it.

Validating arguments (validateArgs)

Walks the schema's properties: drops empty values, coerces digit strings for integer, stringifies string, then checks required. Returns cleaned args or an error the AI gets to fix on retry.

Running once, exactly (executeAction)

  1. Idempotency key = <runId>:<stepId>:<visit>. A loop back increases the visit, so a deliberate re-run gets a new key.
  2. INSERT action_run … ON CONFLICT DO NOTHING. If a row already succeeded, its stored result is returned and nothing runs. A failed row is reset with the new args.
  3. In a transaction with SELECT … FOR UPDATE, it dispatches by source: viasocket_flow → runFlow, viasocket → runAppAction, otherwise the mock handler.
  4. Success marks the row succeeded with the result; failure marks it failed with the error.

Managing actions

PATCH /actions/:key toggles enabled and approval, renames (blocked if any workflow or version uses the key) and edits name/description (which then stop syncing from viaSocket). DELETE removes viaSocket tools only, and only when no workflow uses them.

viaSocket tools

src/integrations/viasocket.ts · integrations.controller.ts · actions.controller.ts from-flow

  1. Builder token: GET /integrations/builder-token signs an HS256 JWT with { org_id, project_id, user_id, unique_identifier } using VIASOCKET_EMBED_SECRET. The web app mounts viaSocket's builder with it.
  2. Tool created or edited: the builder posts a window message to the web app, which relays it to POST /actions/from-flow. The server checks the webhook URL matches https://flow.sokt.io/func/<id>, builds the input schema from the tool's OpenAI/MCP definition, and inserts or updates an action with source='viasocket_flow'. New tools start as write with approval required, to be safe.
  3. Tool deleted: deleted outright, or only disabled if a workflow still uses it.
  4. Running a tool: runFlow(url, args) POSTs the validated args as JSON to the flow URL (60 s timeout). The URL itself is the credential; a status of 400 or above is a failure.
  5. Legacy app actions: fill the stored input template with {{args.x}}, decrypt the app connection (AES-256-GCM with POC_ENCRYPTION_KEY), and call the viaSocket SDK's runAction.

Approvals

  • Evidence tasks (@request_approval) ask a person to review something; the decision lands in outputs, and the next condition reads it ("the team approved the photo").
  • Action tasks are opened automatically for any action with requires_approval. The action only runs after approval, in apply(), with mode approved. Until then the bot tells the customer it is waiting for the team, never that it already happened.
  • openTask reuses an existing pending task for the same run and step. /decide only updates a task that is still pending, so a double click can't decide twice.
  • GET /approvals lists tasks with the customer, the workflow and the attachments resolved for review.

GTWY (the LLM)

src/llm/gtwy.ts · src/llm/decider.ts

  1. Login: the server signs an embed JWT ({ org_id, folder_id, user_id }, HS256 with GTWY_ACCESS_KEY) and posts it to /api/embed/login to get a session token, cached until a minute before it expires.
  2. One agent: ensureAgent() reads the agent id from app_setting, or creates, configures and publishes one through the GTWY SDK and stores its id.
  3. Every call: chat(system, user, json) calls GTWY chat completions with that agent and overrides the system prompt per call (configuration.prompt). JSON calls use response_type: json_object and temperature 0. Calls are stateless; the transcript is passed in each time. A 401 retries once with a fresh session.

Playground API

src/playground/playground.controller.ts · conversations.ts

  • POST /conversations creates a chat for a customer (defaults to Alex Kim). GET /conversations lists chats with the latest run status, the last line and the count of pending approvals (the red dot).
  • GET /conversations/:id is the single poll the screen uses: conversation, all messages (including system), runs with their version's steps and graph, the latest run's events, approvals and action runs.
  • POST /conversations/:id/messages posts as the customer (starts or wakes a run). /team-messages posts as a teammate (no wake-up).
  • POST /attachments takes base64 (1 byte to 5 MB), stores the file under UPLOADS_DIR with its sha256; GET /attachments/:id streams it back.

Chat widget API

src/playground/widget.controller.ts

The embeddable chat uses a narrower API under /widget that only touches channel='widget' conversations:

  • POST /widget/conversations { name?, email } requires an email and returns only the id and name.
  • GET /widget/conversations/:id returns messages without system rows, plus a typing flag and a waiting_approval flag. No runs, events or approvals are exposed.
  • POST /widget/conversations/:id/messages goes through the same postCustomerMessage as the playground.

Run panel and observability

  • Timeline: every meaningful thing is a run_event (run_started, llm_decision, action_called, action_result, case_chosen, goto_jumped, waiting, message_sent, input_received, response_saved, approval_requested, signal, …), with the block id and actor. The run panel draws it directly.
  • Steps view: the panel marks a block done if an event names it, highlights the cursor in yellow, shows chosen cases, saved variables and input answers, and strikes through blocks the run can no longer reach (computed client-side from the graph).
  • DBOS checkpoints: GET /runs/:id/dbos-steps lists the durable steps DBOS recorded for run:<id> (name, output, error, timing), to see exactly what would be replayed after a restart.
  • Tool calls: action_run keeps args, result, error, mode and visit for every call.

Known gaps

Fine for a POC; worth fixing before anything like this ships.

  • highNo authentication on any endpoint, including the public widget API, attachment downloads and approvals.
  • highviaSocket flow URLs are stored in plain text and act as credentials.
  • mediumTool HTTP calls run inside a database transaction holding a row lock (up to 60 s for flows).
  • mediumThe "wants a human" routing outcome doesn't create an escalated run, so the next message is routed again instead of the bot staying quiet.
  • mediumRun control signals (pause, resume…) use a time-based idempotency key, so a double click sends two signals.
  • lowAttachment ids on messages aren't checked against the conversation; uploads aren't type-checked.
  • lowOnly decryption exists for app_connection; there is no code path that creates those rows any more.
  • lowLeftovers: a migration mentions sheet_refund_order; scripts/smoke.js "sheets" mode uses order 5001; stale dist/ files from removed modules.
